# Daily Notes built-in plugin implementation plan

**Goal:** Ship the first CoWiki plugin, Daily Notes, without converting any other module.
**Spec:** [Approved scope](../specs/2026-11-02-daily-notes-plugin.md).
**Architecture:** Register trusted built-ins in one composition root. Shell code consumes registered actions and settings; only the plugin knows that Today opens an editable date page. The ordinary Markdown helper shared with Tasks is not a second plugin.
**Tech stack:** Existing React, TypeScript, local Tauri IPC, Node tests and browser acceptance; no extra production dependency.

## Global constraints

Preserve `features.modules.journal`, existing journal directory/date format/template, default enablement and device-local launch preference. Keep Tasks, Flashcards and drawing native to their present surfaces. No remote code, marketplace, date-navigation feature, implicit commit, or publication. Operate on the isolated local branch.

### Task 1: Introduce the built-in host and migrate its first complete vertical slice

- [ ] Add real behavior tests in `web/tests/daily-plugin.test.ts` and register them in `web/package.json`. Show RED before implementation. A synthetic second definition must contribute and dispatch its own action without edits in the shell. Cover disabled, unloaded settings, nonlocal and duplicate registration; no I/O on disabled dispatch/startup. Test the real Today command with a disposable page store: existing and new date paths, template, create-only race, actual read error, stale workspace and explicit root-start preference. Save unrelated settings through the public config adapter and compare with the original values.
- [ ] Implement `web/src/plugins/` with a small typed manifest/registry and Daily Notes. Host responsibilities: list permitted actions for a loaded local Space, resolve an action at invocation time, dispatch optional launch hooks once per application launch without overriding deep links, and expose plugin-owned settings in the current dialog. Reject duplicate IDs; never evaluate files from a Space. Supply a small current-Space page adapter with bounded authority (read, create-only, refresh, open). Journal logic alone computes the date, resolves an optional template, distinguishes an absent note from another read failure, and delegates ordinary page opening; no overwrites, even on a concurrent create. Example expectations: `assert.deepEqual(disabledActions, [])`; `assert.equal(stored.get(existingPath), originalText)`. Keep the integration ready for a second built-in without adding that plugin to production.
- [ ] Modify `web/src/pages/MainLayout.tsx`, `web/src/components/layout/SpacePanel.tsx`, `web/src/components/SpaceFeaturesDialog.tsx`, and `web/src/lib/space-features.ts`. Remove hardwired Today/startup/Journal settings rendering in favor of contributions; do not migrate Tasks/Flashcards/drawing. Retain Tasks “add to today” via a shared date-page helper. Expose pending configuration as not ready; prevent a slow action from navigating across Spaces or launching after disable; preserve unknown keys on a settings write and reject it on read failure. Existing Markdown remains readable/editable from the tree with the plugin disabled.
- [ ] Document how to add a trusted built-in (small concrete example), what is not an installable plugin, compatibility and data retention. Run focused tests first; then from `web`, `npm test`, `npm run lint`, `npm run build`. No push. Commit implementation/tests and report red/green evidence. Controller verifies app interaction with disposable desktop IPC fixtures and is responsible for integrating the independent native fix.
