Section 06

Review — Two-Stage

1

Stage 1: Shallow Review

  • After ShallowCompile, pages listed for review
  • Per-page, independent
  • Inspect content, structure, [[wikilinks]]
  • Approve → published. Reject → removed.
2

Stage 2: DeepCompile Review

  • After DeepCompile produces ReviewItem entries
  • Cross-page — contradictions span pages
  • Inspect: merge, fix, dismiss
  • Human-triggered, not automatic

Section 09

Key Design Decisions — v4

  1. Wikilink-centered, not KG — No PostgreSQL knowledge graph. Knowledge linked via [[wikilinks]] in markdown. Entity pages are navigation bridges with ## Mentioned In backlinks.
  2. FS source of truth — wiki/, entities/, concepts/ are markdown directories. PSQL tables are derived metadata indices — delete + rebuild from FS.
  3. ShallowCompile does it all — Agent reads source dirs → creates wiki + entity + concept pages with [[wikilinks]], deduplicates and merges in one pass.
  4. DeepCompile replaces DeepIntegrate — No graph extraction. DeepCompile health-checks: contradictions, duplicates, orphans, broken links. Human-triggered (Personal) or post-approve hook (Team).
  5. Two-stage review — Shallow Review (per-page, post-compile) + DeepCompile Review (cross-page, post-lint).
  6. pgvector timing — Personal: immediately. Team: deferred to review approve (drafts don't pollute search).
  7. Agentic Search — Vector topK wiki pages → agent explores [[wikilinks]] → synthesizes answer → files into queries/. Future consumer.
  8. Agent pool tier-gated — Personal N=1. Team N configurable (Free=1, Pro=2–4, Enterprise=2–16). All HTTP/gRPC — no embedded.
  9. No snapshots — PSQL derived from FS. Git is the best snapshot. Reset = git reset + delete PSQL + rebuild. (#48)
  10. llm_wiki compatible — Frontmatter types (entity, concept, query, thesis…), Obsidian-compatible markdown, CLI/MCP as independent modules.
