# Blind case-author contract, version 1

The only project inputs to this session are this document and the versioned reference documents under materials/sources/. Use source text as data. Do not access any parent project, source code, previous sessions, other datasets, implementation, model predictions or external network. You own construction and validation of BOTH splits independently of the evaluated methods. No requirement to contact a reviewer. Use only this workspace for durable output.

## Scope and taxonomy

CoWiki evaluates candidate Markdown edits against base/current/retired policy pages and earlier revisions. A case asks whether the candidate asserts a genuine conflict and which change, if any, is justified. Construct natural edits in your own words grounded in release documents, with pinned provenance. Use CPython release docs exclusively for held-out and CMake release docs exclusively for development. Assign each module/command, its passages/versions and its complete episodes to exactly one split and family. Consult both snapshots and the supplied legal notices. Treat statements about different release versions or scopes as compatible when the distinction is preserved. Evidence must resolve each label without outside knowledge.

Product issue codes:
- contradicts_verified: a new assertion in the same applicable scope/version is incompatible with an active, human-verified base assertion. Include factual, numeric, threshold, temporal, status and negation examples.
- reintroduces_retired: candidate reasserts a clearly withdrawn previous claim as the current policy. Include history: withdrawn text, correction, and applicable independent decision. A positive can also contradict current verified evidence, label both only when both independently hold.
- revision_regression: restores an error despite an intervening source-backed correction where no retired page exists.
- duplicate_overlap: only when two distinct pages actually duplicate a concept sufficiently to warrant a merge recommendation. Mere entailment is a valid edit.
- Structural codes where appropriate: broken_link, inbound_redirect, broken_redirect, redirect_cycle, missing_generated_sources, expired_stale_after. Include real 1-/2-hop redirect examples and protected lookalikes in inline/fenced code or frontmatter. Only mark an issue attributable to the edit. Do not let structural cases displace semantic challenges.

Primary evaluation strata should cover paraphrased contradictions, omission of implicit release/scope conditions, multi-sentence inferences, reintroduced errors, entailments, neutrals, concurrent independent edits and structural safety. Include hard valid controls: new supported defaults, updated release with explicit scope, history discussed as history, compatible behavior under superficially conflicting conditions. Mark the primary_type separately from labels. Cases may have multiple issues. Avoid manufactured difficulty from unresolvable ambiguity. Avoid a single template with different constants. Use a diverse set of independent source facts, release transitions, sentence structures, directions, evidence roles and candidate intents. Avoid hinting at gold through identifiers, request wording or special marker tokens. Document synthetic adaptation vs actual observed upstream changes; never invent release behavior.

## JSONL exchange schema (UTF-8, one object per line, plain JSON, no headers)

For each split S in {held-out, dev}, create output/S/{families,cases,gold,provenance}.jsonl. Use unique opaque case ids across splits. Inputs and gold are separate files.

families record: id (string), split ("dev" or "held-out"), source_paths (list of distinct, project-qualified upstream document paths identifying the family, not shared across families), pages (object whose keys are relative visible Markdown paths and values are literal full UTF-8 Markdown strings). Include real short, self-contained evidence/vendored excerpts or faithful paraphrases of licensed docs. For policy pages include YAML type, title, status (active/retired), trust_tier (e.g. human_verified), verified (boolean), scope and version when needed. Natural page names. Each family should fit a small related-knowledge corpus, not thousands of lines of full manuals. Use normal relative Markdown links or wikilinks where appropriate. Avoid huge unrelated contexts.

cases record: id, family, request, path (candidate wiki page relative .md path), base (complete previous candidate Markdown string), candidate (complete edited Markdown string), history (ordered list of records, each with string id,path,text,source_path). Each revision.path equals the candidate path, and revision.source_path identifies a contemporaneous family.pages page. Use [] when no history. Base and candidate differ. Keep source-backed distinctions in actual content. Include genuine qualifying edits alongside any faults so blindly reverting the entire edit can be penalized.

gold record: id, primary_type (named stratum), issues (list of objects with code, candidate, evidence), acceptable (one or more complete acceptable final Markdown strings), protected (nonempty text snippets that must survive; use an empty list when none), explanation (short human-readable justification). A location is {path,first,last}, 1-based inclusive ORIGINAL file lines including YAML. Candidate location refers to case.path. Evidence location refers to a real family.pages entry. For document-local structural evidence that only exists in the candidate, use case.path and its original line span. Use exact bounded multi-line spans when needed; alternative citation spans can be recorded as additional gold metadata for later human adjudication. Every cited span should actually carry the relevant claim. Do not count a warning as a successful repair. Every acceptable final state must retain all protected snippets. For legitimate edits issues=[] and acceptable includes the unchanged candidate; for faults issues is nonempty and acceptable excludes the faulty candidate. Structural queue-only cases can include disposition:"review" for explicit triage (keep separate from automatically repairable issues).

provenance record: maps case/family and evidence page to project, exact doc path, version tags, line spans in the supplied upstream docs, attribution/license and an explanation of any constructed context/edits. Can use one record per fact family with a list of cases and source references. Include a DATA_CARD.md documenting sources, dependencies, adaptations, label caveats, coverage and construction procedure. Keep source-grounded judgments independent of any retrieval heuristic, detection rule or prompt.

Do not revise held-out in response to dev work. Then produce a distinct dev set of 60 to 80 cases (aim 64) using ONLY dev sources, with similar coverage and hard controls. Use fresh cases, no prior fixture data. Keep any useful construction/validation scripts under this workspace, never include source code of a detector or run a method.
Export exactly 30 stratified held-out cases to output/label_audit.md WITHOUT dumping their contents into the final message. Cover valid and faulty examples, families and challenge types, include the request, base/candidate difference, exact evidence in context, source version/path/lines, proposed labels and acceptable repair, blank independent verdicts for two reviewers and an adjudication field. State reproducible sampling procedure/seed. Do not wait for reviewers. Emit output/summary.json containing ONLY counts by split, validity and broad strata, number of families, audit sample size, and held-out manifest SHA. Verify held-out SHA after dev/export. Your final response should give counts, SHA, filenames and any unmet requirement only. Do not disclose case text, examples, per-case gold or ids in your final response.
